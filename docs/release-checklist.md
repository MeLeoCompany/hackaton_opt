# Чек-лист перед защитой

Этот список проверяет один и тот же демонстрационный контур перед показом заказчику. Он не
меняет данные автоматически: действия с заявками и планами выполняются диспетчером в
демонстрационном офисе.

## 1. Поднять и проверить контур

```bash
./deploy/local.sh
db/apply_migrations.sh --status
docker compose ps
```

Готовый контур должен отвечать по адресам:

- диспетчер — <http://localhost:5173>;
- приложение бригады — <http://localhost:5175>;
- документация API — <http://localhost:8000/docs>;
- Valhalla — <http://localhost:8002/status>;
- R5 — <http://localhost:8003/health>.

В `db/apply_migrations.sh --status` должно быть `Ждёт: ничего`, а у PostgreSQL, backend,
Valhalla и R5 в `docker compose ps` — состояние `healthy`.

Перед самой демонстрацией проверить свежие ошибки:

```bash
docker compose logs --since=10m backend r5 valhalla postgres \
  | grep -Ei 'error|exception|traceback|fatal|panic' || true
```

## 2. Основной сценарий диспетчера

Для стабильного показа использовать офис «Восток — эксперимент» и контрольный день
17.08.2026.

- Войти диспетчером, открыть заявки и убедиться, что таблица и карта загружаются.
- Открыть справочники: офисы, бригады, типы работ, оборудование, вместимость транспорта.
- Построить план с решателем, доступным на стенде: cuOpt на NVIDIA GPU или OR-Tools без GPU.
- Открыть рассчитанный план, маршруты и карту; проверить время, окна, пробег и линии пути.
- Открыть карточку визита и показать статус, бригаду, окно и необходимое оборудование.
- Утвердить план и разрешить бригаде выезд.
- Создать аварийную заявку в середине дня, выполнить пересчёт с момента `T + 15 минут`.
- Если заявка не помещается, показать подбор реализуемого окна либо перенос на другой день.
- Открыть сравнение исходного и пересчитанного планов.

Не запускать повторный тяжёлый расчёт прямо перед выступлением. Заранее сохранить один
утверждённый план и один пересчёт, чтобы основные экраны можно было показать даже без GPU.

## 3. Оборудование

- В справочнике создать или отредактировать тип оборудования.
- Для каждого транспорта проверить максимальное количество, которое может увезти бригада.
- Задать заявке несколько типов оборудования и количество каждого типа.
- Построить утренний план: на вкладке «Оборудование» должна появиться рекомендуемая выдача
  по бригадам с учётом потребности маршрута, вместимости транспорта и резерва.
- Убедиться, что одна и та же единица не расходуется повторно: суммарная потребность маршрута
  не превышает выданного количества.
- Открыть визит в плане: названия и количества должны совпадать с заявкой.
- В середине дня отметить часть заявок выполненными и добавить заявку с оборудованием.
  Пересчёт должен учитывать оставшуюся часть маршрута и уже выполненные работы.
- Проверить границы: заявка без оборудования, нулевой остаток, потребность ровно в предел
  вместимости, потребность на одну единицу выше предела, два разных типа оборудования.

Текущее количество физически оставшегося оборудования у бригады определяется расчётной
моделью дня. Отдельный ручной учёт фактической выдачи и возврата не показывать как готовую
складскую систему.

## 4. Маршрутизация

- Автомобиль, велосипед и пешеход должны возвращать маршрут Valhalla, а не прямую между
  координатами.
- Общественный транспорт должен возвращать маршрут R5 с пешими участками, ожиданием,
  поездками и пересадками.
- Проверить короткий пеший путь в режиме общественного транспорта: R5 вправе выбрать только
  ходьбу, если она быстрее посадки на транспорт.
- Для маршрута Москва — Кашира проверить электричку и региональный транспорт. У автобуса 381
  геометрия приближённая; это известное ограничение исходных данных, а не времени расчёта.
- Максимальная длительность одного плеча R5 — 240 минут. Она не ограничивает весь маршрут
  бригады и не является временем работы решателя.

## 5. Приложение бригады

- Войти под учётной записью бригады и открыть текущий маршрут.
- Последовательно отметить «выехали», «на месте», «выполнено».
- Проверить, что диспетчер видит изменения без нарушения порядка визитов.
- Проверить отмену или снятие будущей заявки диспетчером: бригада должна получить актуальный
  маршрут, а выполненные и начатые визиты должны сохраниться.

## 6. Браузеры и разрешение экрана

- Chrome: вход, таблицы, карта, карточка визита, справочники и модальные окна.
- Firefox: те же экраны; отдельно проверить отсутствие тёмной полосы у закреплённых столбцов.
- Разрешения: 1920×1080 для защиты и узкое окно около 1365×768.
- После обновления страницы выбранные офис и день должны восстановиться корректно.

## 7. Автоматические проверки

```bash
cd backend
.venv/bin/pytest -q
.venv/bin/ruff check src tests

cd ../frontend
docker compose exec -T frontend node --test tests/*.test.mjs

cd ../mobile
docker compose exec -T mobile npm test
```

Production-сборка перед выкладкой:

```bash
set -a
source deploy/deploy.env
set +a
docker compose -f docker-compose.yml -f deploy/compose.server.yml \
  -f deploy/compose.nogpu.yml config --quiet
docker compose -f docker-compose.yml -f deploy/compose.server.yml \
  -f deploy/compose.nogpu.yml build backend web
```

Для GPU-стенда вместо `compose.nogpu.yml` используется `deploy/compose.gpu.yml`.

## 8. План демонстрации

1. Показать вход и изоляцию офисов.
2. Показать реальные заявки, бригады, навыки, транспорт и оборудование.
3. Открыть заранее рассчитанный план и карту маршрутов.
4. Показать общественный транспорт с реальным расписанием R5 и дорожные режимы Valhalla.
5. Открыть выдачу оборудования и карточку визита.
6. Создать аварийную заявку, пересчитать остаток дня и сравнить версии плана.
7. Перейти в приложение бригады и закрыть один визит.
8. Завершить журналом расчёта: ограничения и решения объясняются, а не скрываются.

Если тяжёлый расчёт R5 занимает несколько минут, продолжить рассказ на заранее сохранённом
плане и вернуться к готовому результату позже. Не нажимать повторный запуск: параллельные
расчёты только увеличат время ожидания.
