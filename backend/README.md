# backend

FastAPI-сервис поверх БД планирования маршрутов.

## Структура (`src/`)

```
api/         — HTTP-слой: роутеры и эндпоинты (FastAPI), по одному пакету на фичу
models/      — ORM-модели (SQLAlchemy), зеркалируют схему из db/init/001_schema.sql
schemas/     — Pydantic-модели запросов/ответов для будущих доменных эндпоинтов
services/    — бизнес-логика для будущих доменных эндпоинтов
repositories/— доступ к данным для будущих доменных эндпоинтов
db/          — engine/session/Base
core/        — конфигурация (настройки из переменных окружения)
```

`api/v1/endpoints/health/` — самодостаточный пример фичи (роутер + схемы + сервис +
репозиторий в одной папке), сквозной проверкой прохождения запроса через все слои:
`GET /api/v1/health/` (liveness) и `GET /api/v1/health/db` (доступность БД).

## Расстояния и время в пути (`services/travel/`)

Два провайдера за одним интерфейсом, выбирает `travel_service`:

- `valhalla_provider` — self-hosted Valhalla (сервис `valhalla` в docker compose),
  матрица через `/sources_to_targets`, геометрия маршрута через `/route`;
- `haversine_provider` — запасной вариант по прямой линии с коэффициентом извилистости
  и скоростью по типу транспорта. Работает всегда, геометрию не даёт.

В каждом ответе есть поле `provider`: цифры двух провайдеров отличаются в разы,
и молчаливая деградация на haversine не должна выглядеть как настоящий роутинг.

### Замеренные особенности (важно для метрики пробега)

- **`/sources_to_targets` — приближённый алгоритм (CostMatrix) и занижает длинные
  плечи примерно на 13%.** Замер: Даниловский → Домодедово по матрице 34.1 км,
  по `/route` 38.97 км. Плечи по отдельности и составной `/route` совпадают точно.
- Отсюда правило: **матрица используется только для решений планировщика**
  (там важны относительные цены), а итоговый пробег в отчёте и линия на карте
  берутся из `/route` — это один вызов на инженера, максимум 15 на план.
- Матрица режется на блоки по 2500 пар на стороне клиента (`MAX_MATRIX_PAIRS`),
  потому что это дефолтный лимит `max_matrix_location_pairs` у Valhalla. Сделано так,
  а не поднятием лимита в конфиге, чтобы `docker compose up` работал из коробки
  на любой машине. 115×115 считается за ~4 с.
- Геометрия маршрутов **не хранится в БД**: она выводится из порядка назначений и
  координат, а хранение создавало бы риск рассинхрона карты с планом.

### Допущение по общественному транспорту

Расписаний (GTFS) у Valhalla нет, поэтому ОТ считается как `costing: bus` — движение
по дорогам с автобусным профилем — плюс фиксированные 10 минут на ожидание.
Это приближение, а не настоящая маршрутизация по расписанию.

## День как ключевой параметр

День выбирается один раз и определяет всё: какие заявки видит диспетчер, кто из исполнителей
в смене и на что строится план. Границы дня считает `core/local_day.py` — от 00:00 по Москве
(смещение из настроек) до 00:00 следующего дня; в БД время лежит в UTC.

Списки заявок и исполнителей принимают `plan_date` и возвращают тех, чьё окно или смена
пересекаются с этим днём. Без параметра возвращается всё — так удобнее смотреть данные целиком.

## Планы (`plans`) и решатель cuOpt

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/plans/days` | дни, на которые есть активные заявки |
| GET | `/api/v1/plans?plan_date=2026-08-17` | планы дня, новые первыми, со сводкой |
| POST | `/api/v1/plans` | `{"plan_date": "2026-08-17"}` — построить план на день через cuOpt |
| GET | `/api/v1/plans/{id}` | план: маршруты исполнителей с пробегом и линией, неназначенные с причиной |
| DELETE | `/api/v1/plans/{id}` | удалить план вместе с назначениями — чтобы пересчитать день заново |

Цепочка построения (`services/planner/`):

1. `planner_loader.py` — **БД -> ProblemInstance** на день: активные заявки с окном в этот день,
   исполнители со сменой в этот день, время — минуты от 00:00 по Москве, матрицы из Valhalla
   по типам транспорта. Если Valhalla недоступна — 503, план по оценке «по прямой» не строится.
2. `cuopt_solver.py` — **ProblemInstance -> cuOpt Python SDK** (`cuopt.routing.DataModel`,
   `routing.Solve`) -> визиты по исполнителям. Заявки, которые не подходят никому, в решатель
   не уходят.
3. `planning_service.py` — **результат -> `plan` / `assignment`**: порядок визитов, время начала
   работ, у неназначенных — причина.

Пробег и линия маршрута в `GET /plans/{id}` считаются через Valhalla `/route` по порядку визитов,
а не из матрицы (матрица занижает длинные плечи). Общий пробег так же считается один раз при
построении плана и хранится в `plan.total_distance_km` — список планов показывает его в строке
плана без пересчёта маршрутов (миграция `db/init/010_plan_distance.sql`).

План показывается по снимку входных данных (`plan.input_snapshot`): правка заявок не меняет
уже посчитанный план. Если заявки нет в снимке (её добавили или перенумеровали после расчёта),
берутся текущие данные — лучше показать план по живым данным, чем не показать вовсе.

**cuOpt считает на видеокарте NVIDIA прямо в процессе бэкенда.** Пакет ставится с отдельного
индекса NVIDIA (extra `solver`, см. «Локальная разработка»); в Docker бэкенду выдаётся GPU
(`deploy.resources` в `docker-compose.yml`). Другого решателя нет: без пакета cuOpt или без
видеокарты построение плана отвечает 503, запасной алгоритм не подставляется.

## Исполнители (`engineers`)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/engineers?plan_date=2026-08-17` | исполнители, чья смена попадает в день; без `plan_date` — все. Навыки — списком номеров `skill_ids` |
| GET | `/api/v1/engineers/{id}` | один исполнитель (404, если нет) |
| POST | `/api/v1/engineers` | добавить; `id` можно не передавать |
| PUT | `/api/v1/engineers/{id}` | изменить, навыки заменяются целиком |
| DELETE | `/api/v1/engineers/{id}` | удалить; 409, если исполнитель есть в плане или событии |

Навыков от 1 до 3 без повторов (ТЗ), транспорт и навыки проверяются по справочникам.

Ошибки сервисов наследуются от общих классов из `core/errors.py` (`NotFoundError` -> 404,
`InUseError` -> 409, `DataError` -> 422 со списком `errors`), обработчики — в `main.py`.

## Заявки (`requests`) и справочники (`references`)

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/references` | навыки, приоритеты, транспорт, типы работ — для выпадающих списков |
| GET | `/api/v1/requests?plan_date=2026-08-17` | заявки, окно которых попадает в день; без `plan_date` — все |
| GET | `/api/v1/requests/{id}` | одна заявка (404, если нет) |
| POST | `/api/v1/requests` | добавить; `id` можно не передавать |
| PUT | `/api/v1/requests/{id}` | изменить |
| DELETE | `/api/v1/requests/{id}` | удалить; 409, если заявка есть в плане или событии |
| GET | `/api/v1/requests/csv-template` | шаблон CSV |
| POST | `/api/v1/requests/import` | загрузить CSV (multipart, поле `file`) |

Ошибки данных приходят как 422 с понятными причинами в `errors`.

### Типы работ и нормативы

Справочник `work_type` — таблица нормативов ТЗ: дорога до клиента/ТКД (`travel_minutes`),
работа на месте (`work_minutes` — технические работы и документы сложены вместе, на месте
это одна непрерывная работа) и базовый норматив (`baseline_minutes` — их сумма, считается
в БД).

У заявки хранится `work_type_id`. Он задаёт **навык**: отдельно навык у заявки не выбирается,
иначе два поля об одном и том же разъезжаются. Длительность работ подставляется из норматива,
но её можно задать своей — заявка бывает тяжелее норматива.

Норматив дороги в планировании не используется: там дорога считается по Valhalla между
конкретными адресами. Он остаётся справочной величиной ТЗ.

**Загрузка CSV атомарная**: если хоть одна строка с ошибкой, не сохраняется ничего, в ответе
список ошибок с номерами строк. Строка с существующим номером обновляет заявку, без номера
или с новым — добавляет. Формат описан в `services/requests/requests_csv.py`: разделитель
«;» (или «,» / табуляция), кодировка UTF-8 или Windows-1251, справочники названием или
номером, время без часового пояса считается московским.

Реальные выгрузки из `Обезличивание/` в этот формат напрямую не ложатся: в них нет
координат и длительности визита, а в таблице `request` это обязательные поля.

## Локальная разработка (без Docker, с дебагом в VS Code)

Postgres всё равно нужен — поднимите его отдельно: `docker compose up -d postgres`
(порт 5432 проброшен на localhost).

```
cd backend
python -m venv .venv
./.venv/bin/pip install -e ".[dev]"
# решатель cuOpt (нужна видеокарта NVIDIA), пакеты с индекса NVIDIA:
./.venv/bin/pip install -e ".[solver]" --extra-index-url https://pypi.nvidia.com
cp .env.example .env   # DATABASE_URL для локального запуска
```

Дальше — через VS Code: F5 → "Backend: FastAPI (debug)" (`.vscode/launch.json`,
интерпретатор `backend/.venv` уже прописан в `.vscode/settings.json`). Есть и вариант
"Backend: FastAPI (reload, no debug)" — с `--reload`, но без надёжной отладки в
дочернем процессе релоадера.

Без VS Code — просто `./.venv/bin/uvicorn src.main:app --reload` из `backend/`
(переменные подтянутся из `.env`).

### Тесты планировщика

```
./.venv/bin/python -m pytest tests/planner -v
```

- `tests/planner/test_cuopt_inputs.py` — что уходит в cuOpt и как разбирается ответ; работает
  без видеокарты.
- `tests/planner/test_cuopt_solve.py` — настоящие расчёты cuOpt на маленьких задачах с понятным
  ответом (навыки, транспорт, окна, конец смены, срочность, число исполнителей, скорость
  транспорта). Без пакета `cuopt` файл пропускается.
- `tests/planner/planner_test_helpers.py` — сборка задач и `constraint_violations`, независимая
  проверка решения по всем ограничениям ТЗ.

Отладка: F5 → "Tests: решение cuOpt (debug)" или "Tests: открытый файл (debug)", брейкпоинты —
в `src/services/planner/cuopt_solver.py`.

## В связке с БД

Из корня репозитория: `docker compose up` — поднимет `postgres` и `backend`
(порт 8000, автоперезагрузка при изменении `backend/src`).

Недостижимые пары в публичной матрице передаются как `null`.
В планировщике они заменяются большим числом; конечное время дороги округляется вверх
до целой минуты, чтобы не разрешать визиты за счёт округления вниз.
Создание заявок и CSV-импорт сериализованы транзакционной advisory-блокировкой.
Запись без номера получает **наименьший свободный номер** (`core/free_id.py`), а не следующий
за самым большим: в реальных выгрузках номера девятизначные, и автонумерация, догоняя их,
выдавала новым заявкам номера вроде 900000013. Номера удалённых записей освобождаются —
удалить заявку или исполнителя из плана или события всё равно нельзя, так что «повторный»
номер ни на что не сошлётся.

Границы времени для целочисленной модели округляются внутрь: начало окна/смены вверх,
конец вниз. Окна без допустимого целого момента начала не отправляются в cuOpt.
Перед сохранением результат независимо проверяется на повторные заявки, совместимость,
время переездов, окна и окончание смены. Нарушение или ошибка выполнения cuOpt возвращают
503, план не записывается. Причина неназначения при наличии подходящих исполнителей
описывает найденный план и не утверждает, что выполнение математически невозможно.
Выдача ID инженеров, как и заявок, сериализована транзакционной advisory-блокировкой,
номер нового исполнителя выбирается так же — наименьший свободный.

## Порядок поступления заявок и исполнителей

Редактирование заявки не меняет её порядок поступления. Новые строки CSV получают порядок
в последовательности строк файла, включая смешанные явные и автоматические ID.
Для записей, существовавших до миграции 007, порядок восстановить нельзя: используется ID.
Перед запуском на существующей БД примените `db/init/007_baseline_comparison.sql` и
`db/init/008_drop_comparison.sql` (команды в `db/README.md`).
