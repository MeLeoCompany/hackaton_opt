# backend

FastAPI-сервис поверх БД планирования маршрутов.

## Структура (`src/`)

```
api/         — HTTP-слой: роутеры и эндпоинты (FastAPI), по одному пакету на фичу
models/      — ORM-модели (SQLAlchemy), зеркалируют схему из db/init/001_schema.sql
schemas/     — Pydantic-модели запросов/ответов для будущих доменных эндпоинтов
services/    — бизнес-логика для будущих доменных эндпоинтов
repositories/— доступ к данным для будущих доменных эндпоинтов
db/          — engine/session/Base
core/        — конфигурация (настройки из переменных окружения)
```

Рядом с `src/` лежит `scripts/` — разовые скрипты, которые запускают руками:
`fetch_metro.py` обновляет схему метро из OpenStreetMap.

`api/v1/endpoints/health/` — самодостаточный пример фичи (роутер + схемы + сервис +
репозиторий в одной папке), сквозной проверкой прохождения запроса через все слои:
`GET /api/v1/health/` (liveness) и `GET /api/v1/health/db` (доступность БД).

## Расстояния и время в пути (`services/travel/`)

Провайдеры за одним интерфейсом, собирает `travel_service`:

- `valhalla_provider` — self-hosted Valhalla (сервис `valhalla` в docker compose),
  матрица через `/sources_to_targets`, геометрия маршрута через `/route`;
- `r5_provider` — матрица времени и подробные маршруты общественного транспорта
  по расписанию из локального R5;
- `haversine_provider` — запасной вариант по прямой линии с коэффициентом извилистости
  и скоростью по типу транспорта. Работает всегда, геометрию не даёт;
- `transit_provider` — прежняя приближённая модель метро и ходьбы, которая используется
  только как явно обозначенный fallback, когда R5 недоступен.

В каждом ответе есть поле `provider`: `r5`, `valhalla`, `transit_estimate` или
`haversine`. Молчаливая подмена настоящего роутинга оценкой запрещена.

### Замеренные особенности (важно для метрики пробега)

- **`/sources_to_targets` — приближённый алгоритм (CostMatrix) и занижает длинные
  плечи примерно на 13%.** Замер: Даниловский → Домодедово по матрице 34.1 км,
  по `/route` 38.97 км. Плечи по отдельности и составной `/route` совпадают точно.
- Отсюда правило: **матрица используется только для решений планировщика**
  (там важны относительные цены), а итоговый пробег в отчёте и линия на карте
  берутся из `/route` — это один вызов на инженера, максимум 15 на план.
- Матрица режется на блоки по 2500 пар на стороне клиента (`MAX_MATRIX_PAIRS`),
  потому что это дефолтный лимит `max_matrix_location_pairs` у Valhalla. Сделано так,
  а не поднятием лимита в конфиге, чтобы `docker compose up` работал из коробки
  на любой машине. 115×115 считается за ~4 с.
- Геометрия маршрутов **не хранится в БД**: она выводится из порядка назначений и
  координат, а хранение создавало бы риск рассинхрона карты с планом.

### Общественный транспорт: R5 + GTFS

Для матрицы планировщика время берётся из R5 с учётом локального GTFS, даты, интервалов,
ходьбы и пересадок. Километры для последнего уровня цели cuOpt берутся из наземной
матрицы Valhalla: быстрый матричный ответ R5 содержит время, но не длину выбранного пути.
Если отдельное расстояние Valhalla недоступно, используется явно приближённое расстояние
по прямой с коэффициентом. Пары, для которых R5 не нашёл маршрут, остаются недоступными
и по времени, и по расстоянию.

Планировщик запрашивает матрицу на начало самой ранней смены исполнителя соответствующего
типа транспорта. Это намеренно практичное приближение: cuOpt пока принимает одну статическую
матрицу на день, а не отдельную матрицу для каждой минуты.

При обычном API-вызове разрешён fallback на `transit_provider`; ответ получает
`provider=transit_estimate`. При построении плана используется строгий режим: ошибка R5 или
Valhalla завершает расчёт, чтобы оценка не попала в оптимизацию незаметно.

Подробный `POST /api/v1/travel/route` использует R5 и возвращает отдельные пешие,
автобусные, железнодорожные, трамвайные, паромные и участки метро. Для каждого участка
доступны геометрия, ожидание, идентификатор маршрута и остановки. В маршруте готового
плана каждое плечо запрашивается на фактическое время освобождения исполнителя после
предыдущей заявки. Если R5 недоступен, API явно помечает прежнюю приближённую модель как
`provider=transit_estimate`.

Пешеходный профиль Valhalla и пешие участки R5 получают одну скорость
`R5_WALKING_SPEED_KMH` (по умолчанию 4,8 км/ч). Графы у движков остаются разными.
Для каждого плеча общественного транспорта сравнивается маршрут R5 с прямым пешим
путём Valhalla; если идти быстрее, ответ содержит один пеший участок и
`provider=valhalla`. Цвет транспортного участка передаётся из `route_color`
активного GTFS и используется на карте. Для метро исходные цвета в нынешнем
GTFS взяты из OSM; перед заявлением о точном соответствии официальной схеме
их нужно сверить с актуальной схемой Дептранса.
Матрица планировщика также сравнивает время R5 с пешеходной матрицей Valhalla и
берёт расстояние выбранного пешего пути, если тот быстрее или R5 не нашёл пару.
Значение `provider=r5` у такой матрицы означает, что R5 доступен, хотя отдельные
пары могут быть выбраны из пешеходной матрицы.

Если R5 не может привязать точку с карты к связному пешеходному графу, backend
проверяет пешие подходы Valhalla к ближайшим остановкам из активного GTFS и к
соседним точкам графа. Среди найденных маршрутов выбирается минимальное полное
время с учётом подхода. Механизм не зависит от вида транспорта в GTFS: при
добавлении автобусов их остановки участвуют в том же поиске. Для локального
запуска путь к архиву задаётся `R5_GTFS_PATH`; в Compose он смонтирован в backend.

## День как ключевой параметр

День выбирается один раз и определяет всё: какие заявки видит диспетчер, кто из исполнителей
в смене и на что строится план. Границы дня считает `core/local_day.py` — от 00:00 по Москве
(смещение из настроек) до 00:00 следующего дня; в БД время лежит в UTC.

Списки заявок и исполнителей принимают `plan_date` и возвращают тех, чьё окно или смена
пересекаются с этим днём. Без параметра возвращается всё — так удобнее смотреть данные целиком.

## Слепок дня

День выгружается в CSV и загружается обратно — тем же днём или другим. Файлы заявок
(`services/requests/requests_csv.py`) и исполнителей (`services/engineers/engineers_csv.py`)
в одном формате: колонки читаются и пишутся одним модулем, поэтому выгруженный файл
всегда загружается обратно.

Если у загрузки указан `plan_date`, файл кладётся в этот день **копией**: время суток
сохраняется (включая окна и смены через полночь), даты заменяются на выбранный день,
номера выдаются новые. Так один проработанный день размножается на другие дни, а исходные
заявки и смены не перезаписываются. Без `plan_date` поведение прежнее: строка с существующим
номером обновляет запись, без номера — добавляет.

## Планы (`plans`) и решатель cuOpt

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/plans/days` | дни, на которые есть активные заявки |
| GET | `/api/v1/plans?plan_date=2026-08-17` | планы дня, новые первыми, со сводкой |
| POST | `/api/v1/plans` | `{"plan_date": "2026-08-17", "solver": "cuopt"}` — построить план дня выбранным решателем (`cuopt` или `baseline`) |
| GET | `/api/v1/plans/{id}` | план: маршруты, причины и метрики |
| POST | `/api/v1/plans/{id}/approval` | утвердить план дня: его заявки закрепляются за этим днём |
| DELETE | `/api/v1/plans/{id}/approval` | снять утверждение: заявки снова доступны другим дням |
| GET | `/api/v1/plans/day-check?plan_date=2026-08-17` | перед расчётом: сколько заявок и какие заняты утверждённым планом другого дня |
| DELETE | `/api/v1/plans/{id}` | удалить план вместе с назначениями; 409, если план утверждён |

Цепочка построения (`services/planner/`):

1. `planner_loader.py` — **БД -> ProblemInstance** на день: активные заявки с окном в этот день,
   исполнители со сменой в этот день, время — минуты от 00:00 по Москве. Valhalla считает
   автомобиль, ходьбу и велосипед; R5 считает время общественного транспорта. Если нужный
   маршрутизатор недоступен — 503, план по запасной оценке не строится.
2. `baseline_solver.py` последовательно отдаёт заявку первому доступному совместимому
   исполнителю в порядке входных данных, без перестановки ранее сделанных назначений.
3. `cuopt_solver.py` — **ProblemInstance -> cuOpt Python SDK** (`cuopt.routing.DataModel`,
   `routing.Solve`) -> визиты по исполнителям. Заявки, которые не подходят никому, в решатель
   не уходят. Для ОТ начальная матрица — снимок на начало смены. `transit_schedule.py`
   проверяет только выбранные плечи через R5 на фактическое время выезда и пересчитывает
   начала работ. Если окна или смена нарушены, уточняет время этих плеч в матрице и повторяет
   cuOpt до `TRANSIT_PLAN_MAX_ATTEMPTS` раз (по умолчанию 4). Если допустимый план не найден,
   возвращает ошибку и не сохраняет неточное расписание. Это проверка допустимости выбранного
   решения, а не глобально точная оптимизация по меняющемуся расписанию транспорта.
4. `planning_service.py` сохраняет результат: порядок визитов, время начала работ, объяснения,
   причины неназначения и измеренное время решателя.

### Параметры расчёта

Расчёт запускается с параметрами (`PlanBuildRequest`): день и решатель — `cuopt` (глобальная
оптимизация на видеокарте) или `baseline` (контрольный алгоритм ТЗ: заявки по порядку, первый
подходящий исполнитель). Для cuOpt диспетчер выбирает одно: что важнее сразу после уровней
приоритета — **максимум заявок** (по умолчанию), **меньше задействованных бригад** или
**меньше пробега**; остальные два критерия идут следом в обычном порядке.

Ярусы приоритетов (`urgent_requests`) стоят первыми всегда: их порядок задают отметки заявок
(docs/algoV2.md), и авария или обещанное клиенту время должны быть сильнее любой экономии.
Политика с другим первым критерием отклоняется (`validate_objective_order`). Все четыре критерия
входят в цель ровно один раз. Экономия выше заявок — осознанный выбор: обычную заявку ради неё
могут и не взять, а заявки с ярусом выше базового (аварийные, согласованные, перенесённые)
останутся в плане. По умолчанию порядок такой: уровни приоритета, все назначения, число бригад,
пробег.

cuOpt получает не приблизительную сумму произвольных весов, а лексикографическую цель:
коэффициент каждого уровня вычисляется из верхней границы суммы всех уровней ниже. Поэтому одна
единица более важного критерия гарантированно перевешивает любое улучшение менее важных. Перед
передачей в cuOpt коэффициенты проверяются на безопасный диапазон `float32`.

Каждый расчёт — **самостоятельный план** со своими параметрами и метриками: время решателя
(`solve_duration_ms`), пробег, сколько заявок назначено и сколько из них срочных. Оба решателя
получают один `ProblemInstance`, то есть одинаковый порядок входных данных и одинаковые матрицы,
поэтому планы сравнимы между собой.

Выбранный порядок сохраняется в `plan.objective_policy` (миграция
`db/init/015_plan_objective_policy.sql`), возвращается в сводке и показывается в списке и
сравнении планов. Для baseline поле пустое: его фиксированный последовательный алгоритм не
притворяется настраиваемой оптимизацией.

### Утверждение плана

Заявка с окном через полночь (23:00–02:00) пересекается с двумя днями, и планы обоих дней
вправе её взять — тогда её выполнят дважды. Поэтому диспетчер **утверждает** один план на день
своего офиса:

- `POST /plans/{id}/approval` ставит `plan.approved_at` и проставляет назначенным заявкам
  `request.approved_plan_id`. У офиса на день может быть утверждён только один план (409, если
  уже есть); у разных офисов дни независимы;
- загрузчик дня (`planner_loader.load_day`) не берёт заявки, закреплённые за планом **другого**
  дня, — свои же заявки остаются доступными, день можно пересчитывать сколько угодно;
- `GET /plans/day-check` заранее показывает, сколько активных заявок уйдёт в расчёт и какие
  заняты: номер заявки, её окно, номер и дата плана, который её забрал;
- `DELETE /plans/{id}/approval` отпускает заявки; удалить утверждённый план нельзя (409),
  иначе заявки остались бы закреплёнными за несуществующим планом.

Схема: `db/init/014_plan_approval.sql`.

### Сравнение планов

Отдельного эндпоинта сравнения нет: в сводке плана уже есть всё, по чему планы сравниваются
(назначено, из них срочных, не назначено, исполнителей, пробег, время решателя), поэтому
интерфейс сравнивает две сводки из списка планов дня. Кто какую заявку выполняет и почему —
в самом плане (`GET /plans/{id}`), в сравнении это не дублируется.

Пары планов в БД не хранятся: колонку `plan.comparison_id` сняла миграция
`db/init/013_drop_plan_pairs.sql`.

**cuOpt считает на видеокарте NVIDIA прямо в процессе бэкенда.** Пакет ставится с отдельного
индекса NVIDIA (extra `solver`, см. «Локальная разработка»); в Docker бэкенду выдаётся GPU
(`deploy.resources` в `docker-compose.yml`). Другого решателя нет: без пакета cuOpt или без
видеокарты построение плана отвечает 503, запасной алгоритм не подставляется.

## Вход и офисы (`auth`, `users`)

Все эндпоинты, кроме `/health` и `/auth/login`, требуют заголовок `Authorization: Bearer <токен>`.

| Метод | Путь | Что делает |
|---|---|---|
| POST | `/api/v1/auth/login` | логин и пароль -> токен и данные учётки; 401 на неверный пароль |
| GET | `/api/v1/auth/me` | кто вошёл: роль, офис |
| GET, POST | `/api/v1/users` | учётки (только администратор) |
| PUT, DELETE | `/api/v1/users/{id}` | изменить или удалить учётку (только администратор) |

**Офис — граница данных.** Заявки, бригады и планы отбираются по офису текущего запроса
в одном месте — зависимость `current_office_id` (`src/api/deps.py`). У диспетчера это офис
учётки: заголовок `X-Office-Id` от него игнорируется. Администратор выбирает офис
заголовком `X-Office-Id`, без него — первый офис справочника. Чужая заявка, бригада или
план по номеру выглядят несуществующими (404), а импорт CSV не даёт обновить запись
другого офиса по совпавшему номеру. Бригады офиса берут только заявки своего офиса.

Роли: `dispatcher` — работа со своим офисом, справочники нормативов и оборудования только
на чтение; `admin` — плюс справочники офисов и оборудования, учётки, любой офис.
Последнего включённого администратора нельзя разжаловать, выключить или удалить; себя
удалить или выключить тоже нельзя.

Пароли — хэш scrypt с солью, токены — подпись HMAC со сроком (`src/core/security.py`,
без внешних зависимостей). Секрет подписи — `AUTH_SECRET`, срок — `AUTH_TOKEN_HOURS`
(12 часов). Первый администратор создаётся миграцией: **admin / admin**.

## Статусы заявок (`request_status`)

Вместо флага «активна» у заявки статус: Новая, В плане, В пути, В работе, Выполнена, Отменена
(`db/init/022_request_status.sql`, `023_request_in_progress_and_history.sql`). В расчёт плана
идут заявки в статусах с `plannable`
(Новая и В плане). Статус меняется только переходами из таблицы `request_status_transition`
(`services/requests/request_status_service.py`): перехода нет в таблице — 422; ручной переход
делает только оператор, системный — только система.

- Утверждение плана переводит его заявки «Новая → В плане», снятие утверждения — обратно.
  Заявки «В работе», выполненные и отменённые при снятии остаются как есть и сохраняют связь
  с планом. Если часть заявок плана с момента расчёта выполнена, отменена или ушла в работу,
  план не утвердится (409 «устарел») — его нужно пересчитать.
- `PATCH /api/v1/requests/status` с `{request_ids, status_id}` — оператор переводит заявки
  ручными переходами («В плане → В пути → В работе → Выполнена», отмена, возврат отменённой).
  Все или ни одной.
- Без разрывов в маршруте: у заявки утверждённого плана «В работе» или «Выполнена» можно
  поставить, только если все визиты перед ней в маршруте бригады закрыты (выполнены или
  отменены), иначе 422 «сначала закройте заявку №…». Несколько заявок маршрута в одном
  запросе проверяются по итоговому состоянию: первую и вторую можно закрыть вместе.
- Отменённую заявку утверждённого плана можно вернуть «В план» — на прежнее место в маршруте,
  без пересчёта (`024_request_return_to_plan.sql`), если план всё ещё утверждён и бригада не
  ушла дальше неё (иначе 422 «верните заявку в «Новая» и пересчитайте план»). «Отменена → Новая»
  отвязывает заявку от плана. В ответе плана у визита есть `approved_plan_id` — за каким планом
  заявка закреплена сейчас; снятые с плана визиты проверка разрывов пропускает.
- Повод пересчитать утверждённый план — в его сводке (`GET /plans`, `GET /plans/{id}`):
  `withdrawn_requests` — заявки его маршрутов, которые с утверждения отменили или вернули в
  «Новая» (`request_id`, `status_id` — как сняли); `new_request_ids` — «Новые» заявки его дня и
  офиса, которых расчёт плана не видел. У неутверждённого плана оба списка пустые.
- Менять (`PUT /requests/{id}`, загрузка CSV поверх существующей) можно только «Новую» заявку:
  в плане, в работе, выполненную и отменённую — нет (422 с причиной), чтобы правка не разошлась с
  маршрутами бригад. Отменённую в «Новая» не возвращают (`026`), а копируют:
  `POST /api/v1/requests/{id}/duplicate` — новая заявка с теми же данными и записью в истории
  «Копия отменённой заявки №…». `?plan_date=` переносит копию на другой день: время суток
  окна то же, дата новая.
- Отмена окончательна (`035`): из «Отменена» переходов нет — ни в «Новая», ни «В плане».
  Работу повторяют копией заявки (`/duplicate`).
- Удалять (`DELETE /requests/{id}`) можно только «Новую» заявку (409 у остальных): заявка
  в плане стоит в маршруте бригады, начатую и выполненную нельзя терять, а отменённая
  объясняет, почему работу не сделали. Ненужную работу отменяют, а не удаляют.
- Справочник бригад — `/api/v1/brigades` (GET/POST/PUT/DELETE; офис — `current_office_id`:
  администратору выбранный, диспетчеру свой; `services/brigades/brigades_service.py`).
  Бригада: название, активна, логин и пароль для мобильного приложения (учётка `app_user`
  роли `brigade`, её имя — название бригады; пустой логин — без входа). Переименование бригады
  переименовывает и её смены; бригаду со сменами не удалить — только выключить (новые смены ей
  не заводят, в приложение она не входит). Смена на день (`/engineers`) — `brigade_id` вместо
  имени; CSV исполнителей по-прежнему с колонкой «имя» — бригада находится по названию в офисе
  или заводится без входа. Учётки бригад в `/users` не видны и не правятся.
- Мобильное приложение бригады — `/api/v1/brigade/*` (только учётка с ролью `brigade`,
  `require_brigade`; диспетчерские роутеры закрыты от неё `require_staff`):
  `GET /days` — дни с маршрутом (маршрутов нет вовсе — `default_day` сегодняшний, чтобы
  в приложении была видна дата), `GET /route?plan_date=` — маршрут бригады из утверждённого
  плана (смены с `engineer.brigade_id` бригады учётки), `POST /visits/{id}/depart|arrive|done|fail` — отметки («Выехали» → «В пути»,
  «На месте» → «В работе»): переход статуса по таблице,
  время — в `request_fact` (`services/brigade/brigade_service.py`).
- Выезд бригады закрыт, если она выбилась из плана (`services/planner/departure_gate.py`,
  `docs/algoV2.md`, шаги 7-9): не отметила «Выехали» через `DEPARTURE_GRACE_MINUTES` после
  планового времени, к следующей заявке уже не успеть до конца окна или есть неутверждённый
  пересчёт. В приложении бригады у визита `can_depart` и `blocked_reason`, отметка «Выехали»
  в этом случае отбивается ошибкой. У маршрута в плане — `waiting_request_id` и `waiting_reason`
  («с 12:05 · не выехала по плану · ближайшая заявка №15») и `phone` бригады: оператор звонит
  и либо разрешает выезд — `POST /api/v1/plans/{id}/visits/{request_id}/departure`, — либо
  пересчитывает.
- Отменённый визит в приложении бригады объясняется: `cancel_reason`, `cancelled_at` и
  `cancelled_by` («диспетчером», «бригадой», «системой») — из истории статусов (шаг 11).
- Факт и отставание: у визитов плана `departed_at`, `arrived_at`, `finished_at`; у маршрута
  утверждённого плана `delay_minutes` и `at_risk_request_ids` — на сколько бригада отстаёт по
  своим отметкам и к каким заявкам уже не успеть до конца окна
  (`services/planner/route_delay.py`; «сейчас» учитывается только у плана на сегодня).
  В сводке плана `at_risk_request_ids` — ещё один повод пересчитать.
- Утверждение снимается (`DELETE /api/v1/plans/{id}/approval`), только пока по плану не работают:
  его день ещё не наступил и ни одна бригада не отметилась (`plan_in_work`). Иначе 409 — маршрут
  пропал бы у едущей бригады; такой план меняют только пересчётом. В сводке плана это
  `can_cancel_approval`, а `replaced_by_plan_id` — какой утверждённый пересчёт его заменил:
  по паре `parent_plan_id` / `replaced_by_plan_id` собирается цепочка планов дня.
- Пересчёт с текущего момента — `POST /api/v1/plans/{id}/replan` с `{solver, objective_order}`
  (`services/planner/replan_service.py`): момент берётся по системным часам, `at` в запросе
  нужен только для тестов и разбора инцидентов. Если день плана уже закончился — 400: выполненные, отменённые и начатые заявки
  остаются за бригадами первыми в маршруте, бригада стартует с заявки, где работает (свободна,
  когда закончит), или с последней выполненной, не раньше момента пересчёта; не начатые и
  «Новые» заявки дня решатель раскладывает заново. Получается план `replanned` со ссылкой на
  пересчитанный. Его утверждение (`approve_replan`) заменяет прежний план (`superseded_at`),
  перезакрепляет заявки, «Новые» из разложенных — «В плане», а не поместившиеся «В плане» —
  «Новая» с записью в истории. Если после пересчёта бригады отметили что-то по разложенным
  заявкам — 409, пересчёт устарел.
- Перед пересчётом — пробный: `POST /api/v1/plans/{id}/replan/preview` (те же параметры) считает
  то же самое, откатывает и отдаёт `unassigned` — заявки, на которые не успеваем, с причиной,
  отметкой `expired` (окно уже закрылось) и предложением `suggested_start / suggested_end /
  suggested_engineer`. Предложение — это второй расчёт (`services/planner/window_suggestions.py`,
  `docs/algoV2.md`, шаги 2-3): невлезшим заявкам окно раскрывается в `[max(t0; T); самый поздний
  конец смены]`, а ярусы защищают тех, кто уже влез, поэтому раскрытая заявка никого не вытесняет.
  В базе раскрытие не сохраняется.
- По каждой заявке из `unassigned` оператор обзванивает клиентов и шлёт `decisions` пересчёта
  (шаг 4): `agree` — клиент согласен на предложенное окно (окно сужается до обещанного, заявка
  получает отметку «согласовано»), `move` — сегодня не может (окно на другой день, отметка
  «перенесена с ...»), `cancel` — работа не нужна (отмена с причиной), `no_answer` — не
  дозвонились (тоже отмена, но с отметкой «требует уточнения»). Решения применяются в одной
  транзакции с расчётом: расчёт не получился — не меняется ничего. Решать можно только о «Новых»
  без плана и не начатых «В плане» этого плана. Если после решений раскладывать нечего (всё
  закрыто, начато или перенесено на другой день), пересчёт всё равно считается и сохраняется —
  пустым, из одних закреплённых визитов: иначе ошибка «нечего планировать» откатила бы перенос
  вместе с расчётом.
- Ярусы целевой функции идут от отметок (`services/planner/planner_problem.py`, `objective_rank`):
  аварийные → «согласовано» → P2 «перенесена» → P3 «перенесена» → P2 → P3 → общий хвост. Отметки
  живут на заявке, поэтому перенесённые и согласованные с прошлых дней учитываются сами.
- `free_at` пересчёта — `[{engineer_id, free_at}]`: когда бригада освободится со слов оператора.
  Застрявшая бригада не уложится в норматив, и план считается от этого времени (шаг 10).
- В сводке плана `broken_promises` — заявки с отметкой «согласовано», которые новый расчёт не
  поставил в обещанное окно (или не взял вовсе). Обещание срывается только с ведома оператора:
  интерфейс спрашивает до утверждения (шаг 5).
- `GET /api/v1/requests?plan_date=` отдаёт заявки, окно которых попадает в день, **и** заявки,
  перенесённые с этого дня (`moved_from`): иначе после переноса заявка молча исчезает из дня.
  Выгрузка дня в CSV берёт только заявки самого дня — это слепок его окон.
- Каждая смена статуса пишется в `request_status_history` — кто, когда, вручную или
  системой, по какому плану. `GET /api/v1/requests/{id}/history` — история заявки по порядку.
- Совместимость, пока интерфейс не перешёл на статусы: в ответе заявки есть и `status_id`,
  и `is_active` (следует из статуса); `PATCH /api/v1/requests/active` включает заявку как
  «Отменена → Новая» и выключает как «Новая / В плане → Отменена»; колонка «активна» в CSV
  значит то же самое. Правкой заявки (`PUT`) статус не меняется.
- Справочник статусов и переходов приходит в `GET /api/v1/references`
  (`request_statuses`, `request_status_transitions`).

| GET | `/api/v1/engineers/{id}` | один исполнитель (404, если нет) |

Одна бригада — одна смена за раз: смену, пересекающуюся по времени с другой сменой той же
бригады, не завести ни в интерфейсе, ни файлом CSV (`check_brigade_is_free`,
`brigade_shift_problems`).
| GET | `/api/v1/engineers/csv-template` | шаблон CSV |
| GET | `/api/v1/engineers/export?plan_date=2026-08-17` | выгрузить исполнителей дня в CSV |

Навыков от 1 до 3 без повторов (ТЗ), транспорт и навыки проверяются по справочникам.

Оборудование бригады — список `equipment` из пар `{equipment_id, quantity}` (что и сколько
везёт; пусто — ничего), типы проверяются по справочнику, повтор типа — 422. При правке
количества меняются на месте, а не удаляются и вставляются заново: иначе строка с тем же
ключом упёрлась бы в первичный ключ. В CSV исполнителей — необязательная колонка
«оборудование»: «Роутер: 3, ТВ-приставка: 1» (без количества — одна штука); нет колонки —
запас существующей бригады не меняется. В справочнике оборудования рядом с числом заявок
показано, у скольких бригад оно есть (`engineer_count`); такой тип не удалить.

Бригада принадлежит офису того, кто её завёл (`office_id` в ответе, из запроса не берётся).
Старт — из своего офиса или своя точка: при `start_at_office: true` бэкенд ставит старт
в координаты офиса, что бы ни пришло в `start_latitude`/`start_longitude`, — планировщик читает
координаты исполнителя, а правду о них знает справочник офисов. В CSV исполнителей
широту и долготу старта можно оставить пустыми — бригада выедет из офиса; необязательная
колонка «старт_из_офиса» (да/нет) задаёт это явно. Выгрузка дня пишет её, так что копия
дня на другой день не теряет старты из офиса.

### Типы работ и нормативы

Справочник `work_type` — таблица нормативов ТЗ: дорога до клиента/ТКД (`travel_minutes`),
работа на месте (`work_minutes` — технические работы и документы сложены вместе, на месте
это одна непрерывная работа) и базовый норматив (`baseline_minutes` — их сумма, считается
в БД).

У заявки хранится `work_type_id`. Он задаёт **навык**: отдельно навык у заявки не выбирается,
иначе два поля об одном и том же разъезжаются. Длительность работ подставляется из норматива,
но её можно задать своей — заявка бывает тяжелее норматива.

Норматив дороги в планировании не используется: там дорога считается по Valhalla между
конкретными адресами. Он остаётся справочной величиной ТЗ.

**Загрузка CSV атомарная**: если хоть одна строка с ошибкой, не сохраняется ничего, в ответе
список ошибок с номерами строк. Строка с существующим номером обновляет заявку, без номера
или с новым — добавляет. Формат описан в `services/requests/requests_csv.py`: разделитель
«;» (или «,» / табуляция), кодировка UTF-8 или Windows-1251, справочники названием или
номером, время без часового пояса считается московским.

Реальные выгрузки из `Обезличивание/` в этот формат напрямую не ложатся: в них нет
координат и длительности визита, а в таблице `request` это обязательные поля.

Администратор меняет минуты норматива: `PUT /api/v1/references/work-types/{id}` с
`{travel_minutes, work_minutes}` (работа на месте — не меньше минуты), диспетчеру — 403.
Базовый норматив — вычисляемая колонка БД, после сохранения он перечитывается. Норматив —
только подстановка по умолчанию (длительность новой заявки, строки CSV без длительности):
у существующих заявок длительность хранится своя и не меняется. Название и навык типа работ
не правятся — навык заявки определяется типом работ при её сохранении.

### Уровни приоритета

Приоритет заявки — один из трёх уровней (`priority.level`): 1 «Аварийный», 2 «Высокий»,
3 «Обычный». Какой уровень получает новая заявка, задаёт тип работ (`work_type.priority_id`):
авария — аварийный, подключение — высокий, дозаказ и ремонт — обычный. Соответствие хранится по
типу работ, а не по навыку: навык «Работы на подключение и дозаказы» объединяет высокий
и обычный уровни. Администратор меняет его в `PUT /api/v1/references/work-types/{id}/priority`
с `{priority_id}`. Заявка без `priority_id` (форма, API, строка CSV с пустым приоритетом)
получает уровень своего типа работ; указанный явно уровень остаётся. Существующие заявки
при смене соответствия не меняются.

В cuOpt критерий «срочные заявки» разворачивается в ярусы по уровням: сначала максимум
аварийных, затем высоких; обычные идут вместе со всеми назначениями
(`build_objective_policy`, `ObjectivePolicy.reward_for`). Новая аварийная заявка в дне
утверждённого плана — отдельная причина пересчитать план (`urgent_request_ids` в сводке плана).
В приложении бригады у заявки есть `priority_level`: аварийные и высокие отмечены плашкой.


## Журнал расчёта: что считается прямо сейчас

Расчёт большого дня идёт минутами — матрицы Valhalla и R5, cuOpt, проверка расписания, — и без
журнала интерфейс выглядит зависшим. Каждый запуск пишет свой ход в `plan_run` / `plan_run_event`
(`db/init/038`, `services/planner/run_log.py`):

- текущий запуск живёт в `contextvar`, поэтому шаги пишет и загрузчик дня, и провайдеры матриц,
  и решатель — без прокидывания параметров через все слои. Запуска нет (тесты, фоновые вызовы) —
  функции журнала ничего не делают;
- каждая запись идёт **отдельной короткой транзакцией**: иначе прогресс не был бы виден, пока
  расчёт держит свою транзакцию открытой;
- сбой журнала не роняет расчёт — он пишется в лог приложения и всё;
- шаги с процентами: чтение заявок и смен (2–10), матрицы по каждому транспорту (10–45,
  внутри — блоки R5 и этапы ОТ: улицы, расписание, пешие подходы), решатель (45–80, внутри —
  попытки и проверка расписания), сохранение плана (80–92), пробег маршрутов (92–99).

Интерфейс придумывает номер запуска заранее и шлёт его в `run_id` вместе с параметрами расчёта
(`POST /plans`, `POST /plans/{id}/replan`, `.../replan/preview`), а потом опрашивает:

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/system/runs?limit=` | журнал расчётов офиса, новые первыми |
| GET | `/api/v1/system/runs/{run_id}` | один расчёт со всеми шагами: по нему рисуется прогресс |

## Системное время и параметры системы

Время сервера берётся из `core/clock.py`, а не напрямую из `datetime.now()`: для демонстрации
его можно перемотать (на год в обе стороны), и тогда «сейчас» сдвигается у пересчёта плана
«с текущего момента», отметок бригад, расчёта опозданий и выбора дня в мобильном приложении.
Пересчёт момент не спрашивает, поэтому демонстрация на данных прошлых дней начинается с того,
что часы ставят в день этих данных. Сдвиг хранится
в таблице `system_time` (034), поднимается при старте приложения и живёт в памяти процесса.

| Метод | Путь | Что делает |
|---|---|---|
| GET | `/api/v1/system/time` | системное время, настоящее время и сдвиг (любой вошедший) |
| PUT | `/api/v1/system/time` | перемотать: `{now}` — поставить на момент, `{offset_seconds}` — сдвиг, 0 — вернуть настоящее (администратор) |
| GET | `/api/v1/system/info` | параметры системы: версии, подключения, настройки, объёмы данных (администратор) |

Перемотка ограничена сутками назад и годом вперёд. `/system/info` проверяет базу, Valhalla, R5
и наличие cuOpt, а строку подключения к базе отдаёт без пароля.

## Локальная разработка (без Docker, с дебагом в VS Code)

Postgres всё равно нужен — поднимите его отдельно: `docker compose up -d postgres`
(порт 5432 проброшен на localhost). Для расчёта общественного транспорта также запусти
`docker compose --profile transit up -d r5`; локальный backend обращается к нему по
`R5_URL=http://localhost:8003` из `.env.example`.

```
cd backend
python -m venv .venv
./.venv/bin/pip install -e ".[dev]"
# решатель cuOpt (нужна видеокарта NVIDIA), пакеты с индекса NVIDIA:
./.venv/bin/pip install -e ".[solver]" --extra-index-url https://pypi.nvidia.com
cp .env.example .env   # DATABASE_URL для локального запуска
```

Дальше — через VS Code: F5 → "Backend: FastAPI (debug)" (`.vscode/launch.json`,
интерпретатор `backend/.venv` уже прописан в `.vscode/settings.json`). Есть и вариант
"Backend: FastAPI (reload, no debug)" — с `--reload`, но без надёжной отладки в
дочернем процессе релоадера.

Без VS Code — просто `./.venv/bin/uvicorn src.main:app --reload` из `backend/`
(переменные подтянутся из `.env`).

## В связке с БД

Из корня репозитория: `docker compose --profile transit up` — поднимет R5, Valhalla,
PostgreSQL, backend и frontend. Backend работает на порту 8000 и автоматически
перезагружается при изменении `backend/src`.

Недостижимые пары в публичной матрице передаются как `null`.
В планировщике они заменяются большим числом; конечное время дороги округляется вверх
до целой минуты, чтобы не разрешать визиты за счёт округления вниз.
Создание заявок и CSV-импорт сериализованы транзакционной advisory-блокировкой.
Запись без номера получает **наименьший свободный номер** (`core/free_id.py`), а не следующий
за самым большим: в реальных выгрузках номера девятизначные, и автонумерация, догоняя их,
выдавала новым заявкам номера вроде 900000013. Номера удалённых записей освобождаются —
удалить заявку или исполнителя из плана или события всё равно нельзя, так что «повторный»
номер ни на что не сошлётся.

### Почему визит стоит здесь

У визита в плане нет текста-объяснения: раньше он был шаблонным и пересказывал правила, которые
и так проверены (`validate_solution`). Вместо него визит несёт факты, из которых интерфейс
собирает объяснение: `available_from` (когда исполнитель освободился — начало смены или конец
предыдущей работы), `window_slack_minutes` (запас до закрытия окна), `shift_slack_minutes`
(запас до конца смены после работы) и `candidate_engineers` (сколько бригад дня подходили
по навыку и транспорту). Всё считается по снимку плана, маршрутизатор для этого не нужен.

Границы времени для целочисленной модели округляются внутрь: начало окна/смены вверх,
конец вниз. Окна без допустимого целого момента начала не отправляются в cuOpt.
Перед сохранением результат независимо проверяется на повторные заявки, совместимость,
время переездов, окна и окончание смены. Нарушение или ошибка выполнения cuOpt возвращают
503, план не записывается. Для неназначенной заявки отдельно различаются отсутствие навыка,
транспорта, невозможность выполнить её даже первым выездом и конфликт с общим расписанием.
Для каждого назначения API объясняет совместимость и место визита в общей оптимизации.
Выдача ID инженеров, как и заявок, сериализована транзакционной advisory-блокировкой,
номер нового исполнителя выбирается так же — наименьший свободный.

## Порядок поступления заявок и исполнителей

Редактирование заявки не меняет её порядок поступления. Новые строки CSV получают порядок
в последовательности строк файла, включая смешанные явные и автоматические ID.
Для записей, существовавших до миграции 007, порядок восстановить нельзя: используется ID.
Перед запуском на существующей БД накатите миграции: `db/apply_migrations.sh`
(пояснения в `db/README.md`).

## Известные ограничения и следующие шаги

- Время поиска и вес пробега нужно откалибровать на полном обезличенном наборе из ТЗ.
  Маленькие демонстрационные данные не позволяют оценить качество и скорость на масштабе
  до 100 заявок и 10–15 исполнителей.
- Перепланирование сохраняет новый план, но интерфейс ещё не подсвечивает изменившиеся
  назначения, порядок визитов и маршруты относительно предыдущей версии.
- Для запуска cuOpt требуется NVIDIA GPU. CPU-решатель и автоматический выбор доступного
  backend планировщика остаются отдельным этапом.
