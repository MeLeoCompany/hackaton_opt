# Схема БД — планирование маршрутов выездных инженеров

PostgreSQL 16, поднимается через `docker compose up` из корня репозитория.
Миграции в [init/](init/) выполняются автоматически при первом старте контейнера
(`docker-entrypoint-initdb.d`): `001_schema.sql` — DDL, `002_seed.sql` — наполнение
справочников, `003_mock_data.sql` — небольшой демонстрационный набор (заявки/инженеры/
события/два плана) на основе реальных адресов из `Обезличивание/*.csv`, чтобы можно было
сразу посмотреть на связи между таблицами; при необходимости чистой БД без демоданных
файл можно удалить или не копировать в `docker-entrypoint-initdb.d`.

Подключение по умолчанию: `postgresql://routing:routing@localhost:5432/routing`.

## Накат миграций

Файлы `init/*.sql` выполняются сами только при первом старте контейнера
(`docker-entrypoint-initdb.d`). На живую БД новые файлы накатывает скрипт:

```
db/apply_migrations.sh            # накатить всё, чего в БД ещё нет
db/apply_migrations.sh --status   # показать, что накачено, а что ждёт
```

Что уже применено, помнит таблица `schema_migration` в самой БД. `001_schema.sql`,
`002_seed.sql` и `003_mock_data.sql` — только для первого старта контейнера: скрипт их
не выполняет (демоданные вставились бы повторно), а при первом запуске отмечает применёнными.
Миграции с `004` и дальше написаны идемпотентно (`IF NOT EXISTS`, `UPDATE ... WHERE ... IS NULL`),
поэтому повторный прогон безопасен.

Скрипт ходит в контейнер `routing_db` (`DB_CONTAINER`), а если тот не поднят — локальным `psql`
на `PGHOST`. Новая миграция = новый файл `init/NNN_имя.sql` со следующим номером; ничего
регистрировать вручную не нужно, скрипт берёт всё, чего нет в `schema_migration`.

## Решения по открытым вопросам

1. **plan / assignment хранятся в БД**, а не только в памяти приложения — это
   единственный способ прозрачно сравнивать optimized / replanned прогоны
   и разбирать причины неназначения задним числом.
2. **Матрица расстояний/времени в пути не хранится** — считается на лету из координат
   и порядка визитов (`assignment.visit_order`), как прямо указано в ТЗ
   («не дублируется»). При необходимости кеширования это отдельное решение вне
   границ текущей схемы.
3. **Источник координат — вне схемы БД.** Входные CSV (см. `Обезличивание/`) содержат
   только адрес и район, без широты/долготы. Координаты для `request.latitude/longitude`
   и `engineer.start_latitude/longitude` получаются геокодированием адреса на этапе
   загрузки данных; при неудаче геокодирования — центроид района как запасной вариант.
   Это решение касается только наполнения, схему не меняет.

## Прочие допущения

- **Единицы**: время — `TIMESTAMPTZ` (хранение в UTC, конвертация на отображение —
  на стороне клиента/приложения); длительность и время в пути — минуты (`INTEGER`);
  расстояние — километры (не хранится, см. п. 2 выше); координаты —
  `NUMERIC(9,6)` (точность ~0.11 м, диапазон проверяется `CHECK`).
- **Идентификаторы**: все PK — `BIGINT GENERATED BY DEFAULT AS IDENTITY`. Это позволяет
  как автогенерацию, так и явную вставку внешних идентификаторов (например, номер
  заявки "Заявка" из исходных CSV) через `OVERRIDING SYSTEM VALUE`.
  `skill` / `transport` / `priority` — `SMALLINT` с фиксированными id (см. `002_seed.sql`),
  чтобы наполнение и код приложения могли ссылаться на них константами.
  Реального внешнего идентификатора инженера в ТЗ не описано — сгенерированный `id`
  этой роли достаточно.
- **Справочники** заполняются один раз и не изменяются приложением — таблицы без UPDATE/DELETE
  в обычном рабочем цикле.
- **event_type / plan.run_type** — реализованы как `ENUM`, а не как справочные таблицы:
  в ТЗ (в отличие от skill/transport/priority) они не выделены в раздел «Справочники»,
  но фиксированный набор значений всё равно должен проверяться на уровне БД, а не
  свободным текстом.
- **Ограничения целостности** (квалификация / время / ресурс, п. 2.2) поддержаны структурой
  данных (`engineer_skill`, сравнимые `TIMESTAMPTZ`, `transport_id`), сами проверки —
  задача алгоритма планирования, не БД.
- Учёт оборудования, возврат инженера в стартовую точку и хранение рассчитанных метрик
  пробега/времени сознательно не включены — см. «Что не входит» в ТЗ.

## Активность заявки (`request.is_active`)

Добавлено миграцией `init/004_request_is_active.sql`: `BOOLEAN NOT NULL DEFAULT TRUE`.
Выключенная заявка хранится как есть, но не должна попадать в сборку задачи планирования —
диспетчер включает и выключает заявки, не удаляя их.

На уже поднятую БД накатывается скриптом (см. «Накат миграций» ниже).

## День и решатель плана (`plan.plan_date`, `plan.solver`)

Добавлено миграцией `init/005_plan_day.sql`: `plan_date DATE` — день, на который построен план
(по московскому времени), `solver TEXT` — чем посчитан (`cuopt`, `baseline`, в будущем CPU fallback).
У уже существующих планов дата проставляется из их заявок.

## Снимки исходных данных планов

`init/006_plan_snapshot.sql` добавляет `plan.input_snapshot` (JSONB).
Новые планы сохраняют координаты, окна и параметры заявок и исполнителей при расчёте.
Открытие старого плана использует снимок, поэтому редактирование данных не меняет его маршруты.
Миграция фиксирует существующие планы по текущим данным; ранее сделанные изменения восстановить нельзя.
На существующую БД миграция накатывается `db/apply_migrations.sh` — до запуска обновлённого backend.

## Порядок поступления заявок и исполнителей

`init/007_baseline_comparison.sql` добавляет `request.input_order` и `engineer.input_order`
с отдельными последовательностями: внешний ID и время окна не определяют порядок поступления.
Для существующих записей миграция фиксирует порядок по ID — исходный порядок неизвестен.
Редактирование не меняет порядок; импорт новых заявок сохраняет последовательность строк CSV.
Снимок нового плана содержит также `request_order` и `engineer_order`.

Та же миграция добавляла `plan.comparison_id` для сравнения базового алгоритма с cuOpt;
базовый алгоритм убран, поле снимает `init/008_drop_comparison.sql`.
На существующую БД обе миграции накатываются `db/apply_migrations.sh` — до запуска обновлённого backend.

Повторный запуск безопасен. Новый Docker volume получает все миграции автоматически;
удалять существующий volume не нужно.

## Сравнение baseline и cuOpt

`init/012_plan_comparison.sql` возвращает `plan.comparison_id` и добавляет
`solve_duration_ms`. Один запуск планировщика сохраняет два плана на одном снимке и одних
матрицах: последовательный baseline и результат cuOpt. Общий UUID связывает пару, а время
решателя хранится отдельно от загрузки данных и построения линий маршрутов.

## Типы работ (`work_type`)

`init/009_work_type.sql` добавляет справочник нормативов из ТЗ и ссылку `request.work_type_id`.
Технические работы и документы сложены в одну колонку `work_minutes`: на месте это одна
непрерывная работа, а планировщику важна только её длительность. Дорога до клиента/ТКД лежит
отдельно (`travel_minutes`) — в плане дорога считается по Valhalla, норматив нужен как
справочная величина. `baseline_minutes` — генерируемая колонка, сумма дороги и работы.

Каждый тип работ ссылается на навык, которым его выполняют, поэтому навык заявки не
дублируется вручную, а определяется типом работ. Существующим заявкам миграция проставила
тип работ по их навыку, длительности не трогала.

На существующую БД миграция накатывается `db/apply_migrations.sh`.

## Пробег плана (`plan.total_distance_km`)

`init/010_plan_distance.sql` добавляет общий пробег плана по дорогам. Он считается при
построении плана, чтобы список планов показывал его без пересчёта маршрутов. У планов,
построенных до миграции, поле пустое — такие планы достаточно пересчитать.

`init/011_plan_distance_provider.sql` добавляет источник пробега: `valhalla`,
`haversine` или `mixed`. Поэтому fallback остаётся рабочим, но приближённая цифра
больше не выглядит как точный дорожный расчёт.

## Пары планов убраны (`013_drop_plan_pairs.sql`)

Расчёт больше не строит пару baseline + cuOpt: каждый запуск даёт отдельный план, а сравнение
любых двух планов дня считается на лету по их номерам. Поэтому `plan.comparison_id` и его
индекс сняты.

## Утверждение плана (`014_plan_approval.sql`)

Заявка с окном через полночь (23:00–02:00) попадает в дни по обе стороны полуночи, и планы
обоих дней вправе её взять — тогда её выполнят дважды. Поэтому диспетчер утверждает один план
на день, и его заявки закрепляются за этим планом.

- `plan.approved_at` — когда план утверждён; NULL — черновик. Частичный уникальный индекс
  `plan_approved_day_idx` не даст утвердить второй план на тот же день.
- `request.approved_plan_id` — за каким утверждённым планом закреплена заявка. Планы других
  дней такую заявку не берут. Удалили план — ссылка снимается сама (`ON DELETE SET NULL`),
  и заявка снова доступна любому дню.

## Приоритеты оптимизации (`015_plan_objective_policy.sql`)

Каждый план cuOpt хранит применённый порядок целей в `plan.objective_policy` как JSONB. Это
позволяет воспроизвести расчёт и не сравнивать планы с разными приоритетами как полностью
равнозначные. У старых планов и baseline значение остаётся NULL.

## Офисы (`016_office.sql`)

Справочник `office` — откуда бригады выезжают на смену: название, адрес, координаты.
Наполнен тремя офисами из исходных CSV: в конце каждого файла «Синтетические данные» есть
строка «Адрес офиса», название офиса — регион файла (Восток, Юго-восток, Югоцентр).
Координаты найдены геокодером OpenStreetMap (Nominatim); у двух офисов OSM знает дом только
без строения, поэтому точка стоит на соседнем корпусе того же дома. Уточняются в разделе
«Справочники».

`engineer.office_id` — из какого офиса выезжает исполнитель. Координаты старта при этом
по-прежнему хранятся у исполнителя: их читают планировщик и снимки планов. Бэкенд копирует
их из офиса при сохранении и переносит всем исполнителям офиса, когда офис сдвигают.
Удалили офис — ссылка снимается (`ON DELETE SET NULL`), старт остаётся на месте как «своя
точка». Существующим исполнителям офис не проставлен: их старты с офисами не совпадают.

## Оборудование (`017_equipment.sql`)

Справочник `equipment` — что техник привозит на заявку: название и описание. Для начала два
типа, оба есть в исходных заявках: «Роутер» (подключения, переход на гигабит, дозаказ
оборудования) и «ТВ-приставка» («ТВ. Замена приставки техником»). Правится в интерфейсе.

`request.equipment_id` — какое оборудование нужно для заявки; NULL — не нужно. Внешний ключ
без каскада: тип, который требуют заявки, удалить нельзя, иначе требование молча пропало бы.
Планировщик требование пока не учитывает — запасов оборудования у бригад в модели нет.

## Учётки и офисы как граница данных (`018_accounts_and_office_scope.sql`)

Офис обслуживает свой регион, и диспетчер работает только с ним. Офис не выбирается
в интерфейсе, как день: он приходит из учётки.

- `app_user` — учётки: логин, имя, хэш пароля (scrypt), роль `admin` или `dispatcher`,
  офис (обязателен диспетчеру), флаг `is_active`. Первый администратор — **admin / admin**,
  пароль смените после первого входа.
- `request.office_id`, `plan.office_id` — чьи заявка и план. `engineer.office_id` теперь тоже
  значит «чья бригада» (раньше — «откуда выезжает»); откуда выезжает, говорит новый флаг
  `engineer.start_at_office`: из своего офиса или из своей точки.
- Утверждается один план **на офис и день** (`plan_approved_office_day_idx` вместо
  `plan_approved_day_idx`): у каждого офиса свой день.
- Офис, у которого есть заявки, бригады, планы или учётки, удалить нельзя.

Существующие данные миграция разложила по ближайшему офису: заявку — по адресу, бригаду —
по старту, план — по офису большинства своих бригад. Бригады, у которых уже был указан офис,
получили `start_at_office = true`.

## Несколько видов оборудования на заявку (`019_request_equipment_list.sql`)

Требование оборудования стало списком: таблица `request_equipment` (заявка, тип
оборудования) вместо колонки `request.equipment_id`. Техник может везти, например, и роутер,
и ТВ-приставку. Существующие требования миграция перенесла, колонку удалила. Удалить заявку —
её требования удаляются вместе с ней; тип оборудования, который требуют заявки, удалить нельзя.

## Оборудование бригады (`020_engineer_equipment.sql`)

`engineer_equipment` — что бригада везёт с собой: тип из справочника и количество
(роутеров 3, приставок 1). Удалить бригаду — запас удаляется вместе с ней; тип оборудования,
который есть у бригад, удалить нельзя. Планировщик запас пока не учитывает.

## Количество в требовании заявки (`021_request_equipment_quantity.sql`)

У `request_equipment` появилось `quantity` (сколько штук этого типа нужно на заявку, не
меньше 1) — так же, как у запаса бригады. Существующим требованиям поставлена одна штука.

## Статусы заявок и переходы (`022_request_status.sql`)

Основа пересчёта плана: план утверждён, приходит новая заявка, оператор отмечает выполненные,
пересчёт идёт по тому, что осталось. Флаг `request.is_active` заменён статусом.

- `request_status` — справочник: 1 Новая, 2 В плане, 3 Выполнена, 4 Отменена. `plannable` —
  идёт ли заявка в расчёт плана (Новая и В плане — да). Номера фиксированы, на них ссылается код.
- `request_status_transition` — допустимые переходы (`from_status_id`, `to_status_id`,
  `manual`, `description`). Перехода нет в таблице — он запрещён. `manual = TRUE` — делает
  оператор, `FALSE` — система:

  | Из | В | Кто | Когда |
  |---|---|---|---|
  | Новая | В плане | система | план утверждён |
  | В плане | Новая | система | утверждение снято |
  | В плане | Выполнена | оператор | отметил выполнение |
  | Новая | Отменена | оператор | отмена до планирования |
  | В плане | Отменена | оператор | отмена после утверждения |
  | Отменена | Новая | оператор | отмена снята |

- `request.status_id` — статус заявки (по умолчанию Новая). Миграция разложила существующие
  заявки: выключенные — Отменена, закреплённые за утверждённым планом — В плане, остальные — Новая.

## «В работе» и история статусов (`023_request_in_progress_and_history.sql`)

- Статус 5 «В работе» — бригада выехала на заявку или работает на ней. `plannable = FALSE`:
  как и выполненная, в пересчёт плана она не идёт. Новые переходы (все делает оператор):

  | Из | В | Когда |
  |---|---|---|
  | В плане | В работе | бригада выехала |
  | В работе | Выполнена | отметил выполнение |
  | В работе | Отменена | отмена, когда бригада уже в работе |

- `request_status_history` — каждая смена статуса: `request_id`, `from_status_id` (NULL —
  заявка появилась), `to_status_id`, `changed_at`, `manual` (оператор / система), `user_id`
  (кто сменил или запустил утверждение плана), `plan_id` (по какому плану), `comment`.
  Существующим заявкам миграция поставила одну начальную запись с их текущим статусом.

## Возврат отменённой заявки в план (`024_request_return_to_plan.sql`)

- Новый ручной переход «Отменена → В плане»: отменённая заявка утверждённого плана возвращается
  на своё место в маршруте без пересчёта. Бэкенд пускает, только если план всё ещё утверждён,
  заявка в нём назначена бригаде и бригада не ушла дальше по маршруту.
- «Отменена → Новая» теперь отвязывает заявку от плана (`approved_plan_id = NULL`): она ждёт
  нового расчёта. В утверждённом плане такой визит показывается «Снята с плана».
- Миграция чинит заявки, которые уже стали «Новыми» с привязкой к плану: если план утверждён и
  заявка в нём назначена — возвращает «В план» (с записью в истории), иначе отвязывает.

## Синхронизация дня с планом (`025_day_sync.sql`, убрана в `027_drop_day_sync.sql`)

- Таблица `day_sync` жила недолго: синхронизацию по времени заменили отметками бригад в
  мобильном приложении, `027` её удаляет.

## Отмена окончательна (`026_cancelled_no_return_to_new.sql`)

- Переход «Отменена → Новая» удалён: отменённую заявку в работу не возвращают. Чтобы снова
  выполнить ту же работу, делают копию (`POST /requests/{id}/duplicate`) — новую заявку с теми же
  данными. «Отменена → В плане» (на прежнее место в утверждённом плане) остаётся.

## Учётки бригад и отметки (`028_brigade_accounts_and_facts.sql`)

- `app_user.role` — ещё и `brigade`; `app_user.brigade_name` — чья это бригада (название
  бригады офиса, `engineer.name`: строка `engineer` — смена одного дня, бригада одна на все
  дни). Учётка бригады входит только в мобильное приложение.
- `request_fact (request_id)` — отметки бригады по заявке: `departed_at`, `arrived_at`,
  `finished_at`. По ним карта плана показывает факт и считается отставание от плана.

## Пересчёт с текущего момента (`029_replan_from_now.sql`)

- `plan.parent_plan_id`, `plan.replanned_at` — пересчёт: какой утверждённый план
  пересчитан и на какой момент.
- `plan.superseded_at` — план заменён утверждённым пересчётом. Утверждённым планом дня
  считается только незаменённый: уникальный индекс `plan_approved_office_day_idx` теперь
  `WHERE approved_at IS NOT NULL AND superseded_at IS NULL`.

## Справочник бригад (`030_brigades.sql`)

- `brigade (office_id, name, is_active)` — бригада офиса, постоянный состав; работает в регионе
  своего офиса. Строка `engineer` — её смена на день: `engineer.brigade_id` обязателен,
  `engineer.name` — копия названия бригады (на неё смотрят снимки планов и маршруты).
  Миграция завела бригады из уже существующих смен (по названию в офисе).
- Вход бригады в мобильное приложение — учётка `app_user` с ролью `brigade`, привязанная к
  бригаде (`app_user.brigade_id`, вместо `brigade_name` из 028). Логин и пароль задаются в
  справочнике бригад.

## Уровни приоритета (`032_priority_levels.sql`, `033_priority_names.sql`)

- `priority.level` (уникален): 1 «Аварийный», 2 «Высокий», 3 «Обычный» — чем меньше, тем
  важнее. Названия — степень важности, а не вид работ; по уровню, а не по названию, считают
  срочность решатель, пересчёт и приложение бригады.
- `work_type.priority_id` — уровень по умолчанию для новой заявки этого типа: авария — аварийный,
  подключение — высокий, дозаказ и ремонт — обычный. В заявке уровень можно сменить.
- Заявки со старым «Обычная» при переходе получили уровень своего типа работ; явно отмеченные
  прежним «Срочная» стали аварийными.

## Статус «В пути» (`031_en_route_status.sql`)

- Статус 6 «В пути» — бригада выехала на заявку («Выехали» в приложении), 5 «В работе» — она
  на месте («На месте»). Оба `plannable = FALSE` и ведут себя одинаково: заявка уже занята
  бригадой, в пересчёт не идёт и остаётся за своей бригадой. Переходы: «В плане» → «В пути» →
  «В работе» → «Выполнена», отмена — из любого из них.
