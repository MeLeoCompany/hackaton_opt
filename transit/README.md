# Пилотный GTFS для Москвы

В этом каталоге находится воспроизводимый пилотный набор данных для
маршрутизатора общественного транспорта R5. Valhalla остаётся ответственна за
автомобильные, велосипедные и пешеходные маршруты. R5 использует OSM и
создаваемый здесь архив GTFS.

## Состав пилота

- Локальный каталог 954 автобусных маршрутов, доступных на официальном портале в
  момент ручного сбора.
- Автобусный маршрут `е10` в обоих направлениях на 18, 19 и 20 сентября 2026 года.
  Координаты остановок, геометрия маршрута и все рейсы получены со страницы расписаний
  официального портала Московского транспорта. В будний день найдено 218 рейсов, в
  субботу и воскресенье — по 192 рейса.
- Для `е10` есть **расчётный недельный шаблон** с 1 августа до 31 декабря 2026 года:
  пятничное расписание повторяется ежедневно, включая субботу и воскресенье. Это явно
  помеченное приближение, а не опубликованный календарь перевозчика. Различия по выходным
  и праздничные исключения не учитываются.
  До точных снимков сентября этот шаблон является ретроспективной оценкой для проверки
  планирования, а не опубликованным расписанием автобуса на август.
- 17 обозначений линий и ответвлений Московского метро в обоих направлениях: линии
  `1–12`, `15–17`, а также ветви `4А` и `8А`. Порядок и координаты станций
  получены из маршрутных отношений OpenStreetMap. Их перечень, исходные ID и число
  остановок зафиксированы в `data/metro/network.json`. Официальное время работы
  Московского метрополитена — с 05:30 до 01:00.
- Автобусы `205` и `702` в обоих направлениях: точные снимки пятницы 18 сентября и
  воскресенья 20 сентября 2026 года. В итоговом GTFS ежедневно повторяется только
  расписание пятницы. Выходные снимки сохранены как исходные данные, но в маршрутизации
  не используются.
- МЦК (линия 14) в обе стороны: по 31 станции на круг из направленных отношений OSM.
  Время полного круга 88 минут взято из отношений OSM. Официальный режим работы
  05:30–01:00 и интервалы 4 минуты в пик / 8 минут вне пика взяты с портала
  Московского транспорта; границы пиковых часов и конкретные отправления расчётные.
- Ночные автобусы с [отдельной страницы портала](https://transport.mos.ru/transport/schedule/night)
  собираются с собственным календарным правилом: рейс, отправившийся вечером,
  продолжает маршрут после полуночи под той же датой обслуживания GTFS.
  Ежедневное повторение одного собранного расписания помечается как приближение;
  точный день имеет приоритет над ним.
- Сформированный архив GTFS `generated/moscow-pilot.gtfs.zip`.

Расчётные рейсы метро работают весь 2026 год. Недельные шаблоны выбранных
автобусов действуют с **1 августа по 31 декабря 2026 года** (для ночных рейсов,
идущих после полуночи, доступность первого дня зависит от предыдущей ночи).
Шаблоны основаны на сентябрьских снимках: августовское расписание служит для
испытания планировщика, его нельзя считать подтверждённой историей движения.

Обычные автобусы используют один будний снимок ежедневно до конца периода действия.
Дополнительные выходные снимки сохраняются для возможного развития модели, но не
подменяют будний шаблон в итоговом GTFS. После 31 декабря автобусы не будут доступны,
пока архив не обновят вручную. Интервалы метро и МЦК помечены как
расчётное приближение: Москва публикует режим работы, но не предоставляет стабильное
машиночитаемое расписание каждого поезда. Конвейер использует интервал 2 минуты в часы
пик, 3 минуты днём и 5 минут в начале и конце работы. Указанные в отношении OSM 63
минуты движения по всей линии распределяются между станциями пропорционально
географическому расстоянию. Для линий 16 и 17 в OSM нет общей длительности, поэтому
в них временно принято по 3 минуты на перегон и выставлен признак
`duration_estimated`. Перед эксплуатацией эти значения нужно откалибровать.

Нормализованные файлы JSON отдельно хранят адреса источников, время получения и
принятые допущения. Благодаря этому расчётная частота движения метро не выдаётся за
официальное расписание. При сборке GTFS интервалы разворачиваются в отдельные рейсы:
это позволяет R5 одинаково учитывать метро в матрицах времени и в подробных
маршрутах. Расчётное расписание метро действует с 1 января до 31 декабря года сбора,
чтобы планы на более ранние даты этого же года не теряли метро. Точные автобусные
рейсы действуют только в фактически собранные даты.

## Упрощённые пересадки метро

При сборке GTFS остановочные узлы метро автоматически объединяются в станционные
комплексы. Остановки с одинаковым названием связываются на расстоянии до 700 метров,
а остановки разных линий с разными названиями — до 300 метров. Последнее правило
нужно для комплексов вроде `Кузнецкий Мост / Лубянка` и
`Охотный Ряд / Театральная / Площадь Революции`.

Для каждой группы создаётся родительская станция через `parent_station`. Между
остановками разных линий формируются записи `transfers.txt` с минимальным временем
перехода 5 минут. Это намеренно упрощённая модель для оценки времени поездки бригад:
она не описывает отдельные вестибюли, эскалаторы и коридоры. Штрафы на подход к
станции и выход будут задаваться при подключении R5, поскольку они относятся к
маршрутизации, а не к расписанию GTFS.

## Повторная сборка

Нужен Python 3.12 или новее. Зависимости сборщика лучше установить в отдельное
виртуальное окружение:

```bash
python -m venv transit/.venv
transit/.venv/bin/pip install -r transit/requirements.txt pytest
```

Получение локального каталога маршрутов. Кеш позволяет продолжить работу после
сетевого сбоя, не загружая уже полученные страницы повторно:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-bus-catalog \
  --cache-dir transit/cache/bus-catalog \
  --output transit/data/bus/catalog.json
```

Ночной каталог и расписания всех показанных в нём автобусов:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-night-catalog \
  --output transit/data/bus/night/catalog.json
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-night-bus-batch \
  --catalog transit/data/bus/night/catalog.json --date 2026-09-20 \
  --output-dir transit/data/bus/night
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline repeat-night-buses \
  --catalog transit/data/bus/night/catalog.json \
  --template-date 2026-09-20 --start-date 2026-08-01 --end-date 2026-12-31 \
  --retrospective \
  --output-dir transit/data/bus/night
```

Дата в примере — ночь с 20 на 21 сентября: отправления после полуночи имеют в GTFS
время `24:xx` и далее. Для R5 эти участки также выпускаются отдельными рейсами
следующего календарного дня с временем `00:xx`: так он видит ночной автобус после
полуночи. Если портал не отдаёт одно направление или рейсы на остановках
не согласованы, соответствующий маршрут не включается; причины остаются в
`transit/data/bus/night/collection-report.json`. При обновлении расписаний новые даты
собирают вручную и пересобирают GTFS.

Получение одного автобусного маршрута на выбранную дату (1054 — внутренний
идентификатор `е10` на портале):

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-bus \
  --route-id 1054 --date 2026-09-18 \
  --output transit/data/bus/e10-2026-09-18.json
```

Пакетное получение выбранных маршрутов и дат с проверкой ID и названий по каталогу:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-bus-batch \
  --catalog transit/data/bus/catalog.json \
  --route-id 1054 \
  --date 2026-09-19 2026-09-20 \
  --output-dir transit/data/bus
```

После выполнения создаётся `collection-report.json`. Ошибка одного запроса не
останавливает остальные, но команда возвращает ненулевой код, если хотя бы один
маршрут не был собран.

Для добавления обычного автобуса одной командой укажи его ID и номер на портале,
проверенный будний день и период повторения. Команда получает оба направления,
проверяет исходный файл и создаёт один ежедневный шаблон:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline prepare-bus \
  --route-id 1048 --short-name А \
  --weekday-date 2026-09-18 \
  --start-date 2026-08-01 --end-date 2026-12-31 \
  --retrospective \
  --output-dir transit/data/bus
```

Маршрут А использует расписание одного буднего дня ежедневно, в том числе в
выходные. Это сознательное приближение, отмеченное в исходном JSON. Уже
сохранённая точная дата повторно не скачивается. Для её обновления удали
соответствующий `route-ID-ДАТА.json` перед командой.
Ключ `--retrospective` обязателен, если период начинается до даты исходного снимка.
Для обычного автобуса исходный будний снимок остаётся единственным точным днём в GTFS;
остальные сохранённые снимки этого маршрута не подменяют ежедневный шаблон. Для августа
шаблон даёт возможность тестировать алгоритм, но не подтверждает историческую точность.

Сохранённые вручную страницы направлений складывают в `bus_data/new` с именами
`м1 - 1.html` и `м1 - 2.html`. Для замкнутого кольцевого маршрута вроде `м23`
допустим один файл `м23 - 1.html`; у обычного линейного маршрута отсутствие второго
направления остаётся ошибкой. Команда проверяет ID, дату, направления, остановки и
расписания, создаёт точный снимок и ежедневный шаблон, обновляет перечень автобусов
и переносит обработанные HTML в `bus_data/added`:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline import-bus-html \
  --input-dir bus_data/new --archive-dir bus_data/added \
  --catalog transit/data/bus/catalog.json \
  --output-dir transit/data/bus --inventory bus_data/bus_names.txt \
  --start-date 2026-08-01 --end-date 2026-12-31
```

Если хотя бы одна пара неполна или содержит противоречивые данные, импорт
останавливается до переноса исходников, чтобы ошибочный маршрут не попал в архив.
Порядок уже записанных строк `bus_data/bus_names.txt` импортёр не меняет. Маршрут,
которого ещё нет в снимке официального каталога, разрешается импортировать только
после его явного добавления в этот перечень. Не выбранные для пилота маршруты
фиксируются отдельно в `bus_data/bus_names_dropped.txt`.
Маршруты `Реч1`, `Реч2` и аналогичные сохраняются с типом GTFS `4` (`ferry`),
даже несмотря на то, что каталог транспортного портала относит их к автобусам.

Получение первой линии метро из двух направленных отношений OSM:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-metro \
  --relations 305810 1475755 \
  --output transit/data/metro/line-1.json
```

Получение всех обнаруженных линий метро. Кеш сохраняет сырые ответы Overpass и
позволяет безопасно повторить команду после сетевого сбоя:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-metro-network \
  --cache-dir transit/cache/metro \
  --output-dir transit/data/metro
```

Получение двух направлений МЦК:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline collect-mcc \
  --output transit/data/metro/line-14-mcc.json
```

Сборка всех локальных автобусов и линий метро одной командой и структурная проверка:

```bash
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline build-pilot \
  --output transit/generated/moscow-pilot.gtfs.zip
PYTHONPATH=transit transit/.venv/bin/python -m gtfs_pipeline validate \
  transit/generated/moscow-pilot.gtfs.zip
PYTHONPATH=transit transit/.venv/bin/pytest transit/tests
```

После ручной замены GTFS перезапусти только R5: граф считывается при старте и не
обновляется от изменения файла сам по себе. Для изменения одного расписания
тома OSM и тайлы Valhalla удалять не нужно:

```bash
docker compose --profile transit up -d --no-build --no-deps --force-recreate r5
docker compose --profile transit ps r5
```

Сборщики представляются серверу через `User-Agent`, делают паузу между запросами
направлений, повторяют запросы после временных сетевых ошибок и проверяют, что каждый
рейс движется вперёд во времени. Не следует одновременно загружать все маршруты:
нормализованные результаты нужно кешировать и обновлять контролируемыми порциями.

## Что осталось сделать для эксплуатации

1. При необходимости вернуть отдельные выходные календари на проверенных снимках;
   сейчас для всех обычных автобусов сознательно используется будний шаблон ежедневно.
2. Разделить варианты трасс, укороченные рейсы и маршруты с разным числом отправлений
   на остановках.
3. Сформировать комплексы станций, явные записи пересадок и переходов, затем
   откалибровать время движения, интервалы и пересадки метро.
4. Расширить GTFS: добавить МЦД, монорельс, остальные автобусные маршруты,
   трамваи и другие виды транспорта из источников с понятными условиями
   распространения данных.
5. Запускать официальный валидатор MobilityData и проверочный маршрут R5 в CI.

## Проверочный сервис R5

В `r5_service` находится отдельный HTTP-адаптер над R5/r5py. Его матричный API подключён
к backend для планирования общественного транспорта; сервис запускается через
Compose-профиль `transit`. Сервис
`r5-osm` один раз вырезает Москву и область из PBF Центрального федерального округа,
который уже скачала Valhalla. Это необходимо из-за ограничения R5 на географический
охват исходного графа. Результат хранится в volume `r5_osm`.

Затем R5 строит транспортный граф из этого экстракта и
`generated/moscow-pilot.gtfs.zip`. Подготовленный граф сохраняется в Docker volume
`r5_cache`, поэтому следующие старты не повторяют полную сборку.

```bash
docker compose --profile transit up -d --build r5
docker compose --profile transit logs -f r5
curl -fsS http://localhost:8003/health
```

На тестовой машине первый запуск занял около двух минут и использовал до 7 ГиБ памяти.
Фактическое время зависит от процессора и скорости диска; повторный запуск читает
готовый кеш за несколько секунд.
Готовый сервис отвечает на `POST /route`:

```bash
curl -fsS http://localhost:8003/route \
  -H 'Content-Type: application/json' \
  -d '{
    "origin": {"lat": 55.7888545, "lon": 37.6801752},
    "destination": {"lat": 55.692741, "lon": 37.5331503},
    "departure_time": "2026-09-18T09:00:00+03:00"
  }'
```

Ответ содержит выбранные R5 этапы, ходьбу, ожидание, время в транспорте, пересадки и
геометрию. Для маршрута с метро отдельно добавляются по 4 минуты на вход и выход,
после чего ко всему времени применяется запас 10%. Значения управляются переменными
`R5_METRO_ENTRY_SECONDS`, `R5_METRO_EXIT_SECONDS` и
`R5_RELIABILITY_BUFFER_RATIO`. Скорость пеших участков R5 задаёт
`R5_WALKING_SPEED_KMH` (по умолчанию 4,8 км/ч, одинаково для `/route` и `/matrix`).
Запрос обязательно передаёт время с часовым поясом;
перед R5 оно переводится в московское время.
Сравнение нескольких маршрутов без автобусов с Яндекс Картами и известные
расхождения сохранены в [проверке времени метро](benchmarks/metro_2026-09-19.md).

Для расчёта всех направлений между точками используется `POST /matrix`:

```bash
curl -fsS http://localhost:8003/matrix \
  -H 'Content-Type: application/json' \
  -d '{
    "points": [
      {"id": "engineer-7", "lat": 55.7888545, "lon": 37.6801752},
      {"id": "request-42", "lat": 55.692741, "lon": 37.5331503},
      {"id": "request-43", "lat": 55.753525, "lon": 37.634155}
    ],
    "departure_time": "2026-09-18T09:00:00+03:00"
  }'
```

Ответ сохраняет порядок `point_ids` и содержит две квадратные матрицы в секундах:
`raw_durations_seconds` с медианным временем R5 и `durations_seconds` с добавленным
запасом надёжности. `null` означает, что R5 не нашёл путь в пределах допустимого
времени. Диагональ всегда равна нулю.

Матрица использует отправления из окна 10 минут, максимум 100 точек и маршруты не
длиннее 240 минут. Параметры меняются через `R5_MATRIX_TIME_WINDOW_MINUTES`,
`R5_MATRIX_MAX_POINTS` и `R5_MAX_TRAVEL_MINUTES`. Фиксированное время входа и выхода
из метро применяется только в подробном `/route`: матричный API R5 не сообщает,
какой вид транспорта победил для отдельной пары, поэтому применение этого штрафа ко
всем автобусным и пешим поездкам было бы ошибочным.

Для планов с числом точек больше `R5_MATRIX_MAX_POINTS` бэкенд последовательно
вызывает `POST /matrix-block` с отдельными наборами начал и концов маршрутов.
Блок ограничен `R5_MATRIX_BLOCK_MAX_PAIRS` парами (по умолчанию 2500); бэкенд
выбирает до `R5_MATRIX_BLOCK_ORIGINS` начальных точек (по умолчанию 20) и
автоматически делит конечные точки, затем собирает полную направленную матрицу.
Порядок ID и размеры каждого ответа проверяются: ошибочный блок не подменяется
приближёнными значениями. Блоки выполняются последовательно, поэтому большая
матрица может считаться несколько минут. Лимит одной обычной квадратной матрицы
синхронизирован через `R5_MATRIX_MAX_POINTS` в обоих контейнерах.

R5 и r5py закреплены по версиям, а наружу выставлен наш API: у самого R5 нет
стабильного публичного HTTP-контракта. Дорогие подробные маршруты и матрицы
последовательно используют один экземпляр JVM, чтобы параллельные запросы не
перегружали процесс.

Граница экстракта по умолчанию — `35.0,54.1,41.0,57.0`; она покрывает Москву и
Московскую область. Её можно изменить через `R5_OSM_BBOX`. После изменения границы
или обновления исходного PBF нужно удалить volumes `r5_osm` и `r5_cache`, затем снова
запустить профиль `transit`.
